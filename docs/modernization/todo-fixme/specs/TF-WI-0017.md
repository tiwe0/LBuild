# TF-WI-0017: Add ARM64 memref CAS and DCAS builtins

## Scope

`Lambda64/compiler/backend/arm64/memory.lisp:77`.

## Current boundary

Single-word raw memref CAS is implemented through the ARM64
`arm64-cas-mem-instruction`. DCAS cannot yet be lowered: although the LAP
assembler defines `casp[a][l]` encodings, the backend has no 128-bit
compare-exchange IR instruction carrying an arbitrary address, paired
old/new/current virtual registers, or the required register-clobber and
alignment contracts. The existing `%dcas-object` runtime path is
object-relative and cannot be reused for raw memrefs.

Keep the marker until that IR/codegen/ABI chain and host/guest atomicity tests
exist.

### Minimal implementation design

1. Add an ARM64 128-bit raw-address CAS IR node with two old, new, and result
   operands plus explicit 16-byte alignment validation.
2. Define register-allocation clobbers and pair-register constraints matching
   the `caspal` encoding and memory-order semantics.
3. Lower `(dcas %memref-t)` through that node and add host/codegen and guest
   contention fixtures covering aligned, misaligned, and failure cases.

Current backend evidence: `arm64-cas-mem-instruction` models one old/new pair
and one current output, reports no clobbers, and its emitter only selects
32/64-bit scalar `cas[a][l]` opcodes. The existing `%dcas-object` LAP routine
uses fixed adjacent registers (`x2/x3` and `x6/x7`) plus GC-linked interior
pointer metadata; none of those constraints are represented by the generic
register allocator. Reusing it for `%dcas-memref-t` would therefore permit
misallocated register pairs and incorrect GC maps.

## Required evidence

Add focused code-generation tests plus the relevant host/guest integration test before removing the marker. The test must cover the architectural boundary, unchanged behavior for existing inputs, and failure/overflow behavior where applicable.
