# TF-WI-0151: Virgl scanout resize consistency contract

## Scope

This specification resolves scanout size changes handled by `virgl-reset-1` in
`Lambda64/gui/virgl/virgl.lisp`.

## Required behavior

The first reset creates one scanout wrapper for the virtio-gpu framebuffer
resource. Later resets preserve that wrapper's object identity so contexts and
callers holding the scanout do not retain a stale object. After the GPU has
recreated or resized its framebuffer, the wrapper is updated under the virgl
lock with the current DMA buffer, format, width, height, and render-target
state. The framebuffer resource ID remains the reserved virtio-gpu framebuffer
resource ID.

The wrapper does not release an old framebuffer allocation. Framebuffer
storage is owned and replaced by the virtio-gpu driver, while virgl only tracks
the driver's current allocation. Reset continues to recreate the primary
context, reattach the framebuffer resource, and refresh the capset before
publishing the updated scanout state.

## Test-before evidence

`Lambda64/tests/host/test-virgl-scanout-backing.sh` was first run against the
pre-change source and exited with status 1 at the missing memory-entry
constant. Source inspection also showed that every reset replaced `%scanout`
with a new instance, leaving any previously returned scanout stale after a
framebuffer size or allocation change.

## Acceptance evidence

The focused host test invokes the real `virgl-reset-1` twice. Between resets it
changes the mocked GPU framebuffer allocation, format, width, and height. The
test proves that the scanout object identity and reserved resource ID remain
stable while its backing and dimensions are refreshed, and that capset refresh
still occurs on both resets.

The ledger also requires a guest test. No QEMU virgl display-resize run has
been recorded for this slice, so this work item remains active until a guest
resize demonstrates correct rendering through a previously obtained scanout
reference.
