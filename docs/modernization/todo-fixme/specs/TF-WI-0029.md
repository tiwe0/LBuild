# TF-WI-0029: Model NLX regions accurately in SSA CFGs

## Scope

NLX begin instructions are currently represented as branches to NLX targets, which is insufficient for calls whose dynamic exits remain live. SSA conversion conservatively rejects functions with NLX; retain until dynamic-contour modeling is implemented and tested.

The missing edge is not expressible through the current `successors` generic:
call instructions have an ordinary fall-through continuation as well as
zero-or-more dynamic NLX targets, but the generic method has no enclosing
function/contour argument. Adding target edges directly to every call would
also make non-NLX calls appear to have impossible successors and would alter
dominance and phi placement.

### Minimal implementation design

1. Compute immutable dynamic contours once per backend function.
2. Build an SSA-specific successor relation that augments call instructions
   only when their contour contains a `begin-nlx-instruction`, retaining the
   normal continuation edge.
3. Feed that relation to dominance, liveness, and phi placement without
   changing the generic CFG `successors` protocol.
4. Add fixtures for calls with zero, one, and nested NLX targets, asserting
   equivalent fall-through SSA and rejection of unsafe cross-target phis.

Current implementation evidence: `dynamic-contours` records the active stack
for each instruction by traversing the generic `successors` relation, while
`construct-ssa` invokes candidate discovery before `ssa-convert-locals` builds
dominance/CFG state. No contour snapshot is currently threaded into those
later analyses, so enabling the disabled experiment in
`discover-ssa-conversion-candidates` would mix two different edge models.

## Implementation status (2026-09-13)

Steps 1 and 2 landed; **step 3 did not**.  `compute-actual-successors` exists in
`backend/analysis.lisp` and is consulted by reachability, but neither
`ssa-convert-locals` nor `compute-dominance` uses it -- both still call
`build-cfg`.  The NLX target edges were nonetheless removed from `build-cfg`
and from `successors` on `begin-nlx-instruction`, so the graph SSA walks lost
those blocks entirely rather than gaining a more precise model of them.

Consequence: an NLX thunk had no predecessor, `dynamic-contours` never
propagated any binding's live range into it, and the contour test in
`ssa-convert-one-local-locate-binding-storing-basic-blocks` rejected every
block reachable through it.  Those blocks kept reading each variable's entry
definition.  On ARM64 a loop accumulator following a `handler-case` that
actually unwinds was emitted as `ORR :Xn :XZR :XZR` / `ADDS :Xn :Xn 2` -- the
assignment discarded and the loop non-terminating.  `mezzano.network::resolve-address`
hit this on any hostname lookup, hanging stage-four dependency loading.

The edges have been restored (upstream behaviour) pending a complete
implementation of step 3.  Do not remove them again without simultaneously
threading an NLX-aware successor relation into dominance and phi placement.
Executable evidence: `tools/ci/test-arm64-nlx-ssa-codegen.sh` cross-compiles an
unwinding and a non-unwinding variant and asserts the accumulator is not
constant-folded; `tests/host/test-compiler-ssa-nlx-cfg-boundary.sh` guards the
edge invariant itself.

## Required evidence

Add focused host, compiler/codegen, and (where applicable) cold-image tests
covering success, boundary, and failure behavior before removing the marker.
