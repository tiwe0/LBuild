# TF-WI-0070: Atomic memory-ordering contract

## Scope

This specification replaces the provisional ordering note in
`Lambda64/doc/atomic-extensions.md` with the ordering implemented by the two
compiler backends.

## Required documentation contract

The public atomic macros have no ordering parameter. Arm64 built-ins select the
acquire/release forms (`casal`, `caspal`, `ldaddal`, `ldsetal`, `ldeoral`, and
`swpal`). X86-64 built-ins select locked compare-and-swap and read-modify-write
instructions, plus the atomic memory form of `xchg` for swap. The guide must not
present Rust-style ordering keywords as accepted arguments.

Generic arm64 read-modify-write expansions that use a CAS loop inherit the
ordering of their successful `casal` operation. The contract does not promise a
dedicated machine instruction for every macro and place combination.

The fixed backend behavior applies only to built-in atomic places. A custom cas
function supplies its own atomicity and memory-ordering behavior. The CAS API
does not permit independent success and failure orderings.

## Test-before evidence

Before the documentation change, the ordering section described its contract
as poorly defined and listed prospective keywords without explicitly saying
that the API rejects them. Static source inspection showed fixed instruction
selection in both backends.

## Acceptance evidence

These focused checks anchor the architecture statements to the instruction
selection sites:

```sh
rg -n "lap:(ldaddal|swpal|casal|ldsetal|ldeoral)" Lambda64/compiler/backend/arm64/{object,codegen}.lisp
rg -n ":prefix '\(lap:lock\)|:opcode 'lap:xchg64" Lambda64/compiler/backend/x86-64/{object,cons,memory}.lisp
rg -n 'caspal' Lambda64/runtime/runtime-arm64.lisp
```

`make docs-check` and `git diff --check` provide the repository-level document
and whitespace gates. These static checks validate the current backend contract;
they do not claim a cross-architecture language-level ordering selector.
