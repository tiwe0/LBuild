# TF-WI-0414: Function-reference lock and synchronization boundary

Updating a function-reference currently writes the target and patches its fast
path without an explicit lock, fence, or cross-CPU protocol. These FIXME
markers describe a concurrent runtime correctness gap; removing them requires
a defined publication order and safe readers on x86-64 and ARM64.

Required evidence: concurrent host stress, architecture-specific instruction
ordering review, and guest boot coverage before changing the update sequence.

## Blocking implementation facts (2026-09-01)

`function-reference` has only the four ABI slots (`undefined-entry-point`,
`name`, `function`, `code`); there is no per-reference lock or state word in
`system/data-types.lisp`. The setter is called by `fdefinition`, `fmakunbound`,
tracing, and bootstrap paths, so a new lock cannot be lazily allocated without
an initialization/reentrancy protocol. Existing synchronization primitives are
thread mutexes (`supervisor/sync.lisp`) and architecture-specific
`dma-write-barrier`; neither provides a function-reference publication protocol
or a cross-CPU acknowledgement for readers executing the patched code bytes.
The x86-64 fast path patches a PC-relative displacement while ARM64 readers
load the target and entry point indirectly, requiring separate ordering rules.
Implementing this FIXME therefore needs an ABI slot/state design, publication
state machine (including recursive setter and unbound transitions), and an IPI
or equivalent quiescence/acknowledgement mechanism before source changes are
safe.

## Mutation-aware contract

The marker is guarded by `Lambda64/tests/host/test-system-runtime-support-fref-boundary.sh`.
The host contract checks that all three boundaries remain present in the setter and
that function publication precedes dispatch activation; deleting any marker must
fail the test (the default invocation runs lock/fence/cross-CPU mutations).
