# TF-WI-0134: Block-device UUID host-name namespace contract

## Scope

This specification completes the block-device naming requirement formerly
recorded at `Lambda64/file/fs.lisp:852`. The repository contains no remote
namespace-server client. Its current configuration authority is
`*FILESYSTEMS-ALIST*`, documented by `Lambda64/ipl.lisp` and already consumed
by FAT and ext4 `CREATE-HOST` methods.

## Required behavior

- `FILESYSTEM-NAME-ALIST` returns an isolated snapshot of the configured
  UUID-to-host-name namespace. It recreates every entry and copies mutable
  string UUID and host-name values, so a filesystem implementation cannot
  mutate the authoritative mapping through the value passed to `CREATE-HOST`.
- Each `CREATE-HOST` attempt receives its own copy of the snapshot, so a
  rejecting filesystem class cannot corrupt either the entry structure or
  string values observed by the next registered class.
- `FILESYSTEM-HOST-NAME` performs case-insensitive UUID lookup against either a
  caller-supplied snapshot or a fresh snapshot.
- Existing unmounted hosts retain first priority because they preserve their
  prior host identity and mount arguments.
- If no existing host accepts the device, every registered filesystem class is
  tried with the stable mapping snapshot until one succeeds.
- A configured UUID name takes priority inside FAT/ext4 `CREATE-HOST`; when no
  mapping exists, their existing volume-label and UUID-derived naming fallback
  remains available.
- No undeclared remote lookup, network dependency, or fabricated namespace
  protocol is introduced.

## Test-before evidence

Before implementation,
`FILE_FS_CASE=0134 bash Lambda64/tests/host/test-file-fs-semantics.sh` failed
with `The function MEZZANO.FILE-SYSTEM::FILESYSTEM-HOST-NAME is undefined`.
The mount path passed the mutable global list directly and exposed no controlled
snapshot or query facility.

An isolation regression added after the initial snapshot implementation failed
with `Configured UUID mapping did not take priority (expected CONFIGURED, got
MUTATED)`: a rejecting filesystem mutated the shared attempt snapshot before
the succeeding filesystem ran.

A stricter follow-up changed both UUID and host name to independently allocated
mutable strings and mutated their first characters in place. It failed with
`Configured UUID mapping did not take priority (expected "CONFIGURED", got
AUTO-GENERATED)`, proving that `COPY-TREE` preserved the string leaves and let a
rejecting attempt corrupt later lookup.

## Acceptance evidence

`Lambda64/tests/host/test-file-fs-semantics.sh` extracts the production mapping
and mount functions. It covers case-insensitive lookup, configured-name
priority, snapshot isolation from destructive `CREATE-HOST` behavior, fallback
naming when the mapping is absent, per-attempt isolation across filesystem
classes (including in-place UUID and host-name string mutation), and
existing-unmounted-host priority.
Registration coverage additionally supplies two block devices to
`REGISTER-BLOCK-DEVICE-HOST-TYPE` and verifies that mutation during the first
`CREATE-HOST` attempt cannot change the configured mapping observed by the
second attempt or the authoritative namespace.

The work item remains active until guest tests use real FAT/ext4 block devices.
A future external/network namespace lookup requires a separately specified
protocol and client; no such facility currently exists in this repository.
