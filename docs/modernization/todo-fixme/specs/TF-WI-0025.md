# TF-WI-0025: Support arbitrary closure environments in DX closure IR

## Scope

MAKE-DX-CLOSURE currently models one environment operand shape. Arbitrary environment layouts require closure ABI and serializer/codegen agreement; retain until host and cold-image coverage proves layout compatibility.

## Required evidence

Add focused host, compiler/codegen, and (where applicable) cold-image tests
covering success, boundary, and failure behavior before removing the marker.

## Evidence (2026-09-01)

The IR currently carries one opaque environment value and both target emitters store it into closure slot 2. Supporting arbitrary environment layouts is therefore not an emitter-only change: it requires defining an operand-kind contract (simple-vector, cons, or custom layout), updating closure allocation/slot metadata, and teaching cold serialization how to preserve each representation. Until that ABI is specified, widening this class or bypassing its operand checks would permit mismatched closure layouts.

## Staged design (2026-09-01)

A compatible extension should introduce an explicit environment-layout
descriptor (kind, slot width, and lexical-to-slot map) carried by
`make-dx-closure-instruction`; the existing single environment operand remains
the default opaque pointer form. `lower-environment` must produce descriptors,
and both target emitters plus cold serialization must validate and preserve the
descriptor before writing closure slot 2. The first executable stage is a
host-only descriptor/slot-map fixture for empty, vector, and custom layouts;
only after that passes should codegen changes be attempted. No such descriptor
ABI exists today, so implementation is blocked without a cross-layer contract.
