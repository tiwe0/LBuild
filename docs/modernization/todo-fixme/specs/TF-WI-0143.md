# TF-WI-0143: BITBLT blend SIMD alignment contract

## Scope

This specification closes the alignment dispatch requirement in
`Lambda64/gui/blit.lisp` for `%bitblt-blend-line` on the ARM64 and x86-64 SIMD
paths. It does not claim a measured performance improvement.

## Required behavior

Mezzano heap objects begin on a 16-byte boundary. Runtime allocation in
`Lambda64/runtime/allocate.lisp`, cold-image allocation in
`Lambda64/tools/cold-generator2/serialize.lisp`, and object transport in
`Lambda64/system/gc.lisp` all round an object's header-plus-payload size to an
even number of eight-byte words. Therefore aligned area/TLAB starts and every
following object start remain 16-byte aligned across the runtime, cold image,
and moving-GC paths.

`Lambda64/system/runtime-array.lisp` allocates a simple array's element storage
as the object payload. `object-slot-displacement` in
`Lambda64/compiler/backend/arm64/codegen.lisp` defines payload slot zero as
object base plus eight bytes, and the UB32 SIMD transforms in
`Lambda64/runtime/simd-x86-64.lisp` scale each element index by four bytes.
Thus a UB32 element address is `base + 8 + 4 * offset`, and is 16-byte aligned
exactly when the element offset is congruent to 2 modulo 4.

Before selecting either the 16-pixel interleaved operation or the four-pixel
quad operation, `%bitblt-blend-line` must blend the shortest possible scalar
destination prefix, bounded by the line length, that reaches this boundary.
All subsequent SIMD destination offsets must remain congruent to 2 modulo 4.
If the line ends before the boundary, the complete line is processed by the
scalar operation. The trailing one to three pixels after the bulk operations
also use the scalar operation.

Only the destination offset controls the prefix, so differing source and
destination alignment must not force an otherwise eligible line onto an
all-scalar path. This preserves the existing source-access behavior rather
than adding a new source-alignment requirement. Pixel values and the set of
destination elements modified must remain equivalent to the scalar blend
operation for every start offset and length.

This alignment is not an instruction correctness requirement on x86-64: the
load and store builtins in `Lambda64/compiler/backend/x86-64/simd.lisp` use
`MOVDQU`, which supports unaligned addresses. ARM64 emits `LDR`/`STR` for
quad access and `LD4`/`ST4` for interleaved access through
`Lambda64/runtime/simd-arm64.lisp` and
`Lambda64/compiler/backend/arm64/codegen.lisp`; the dispatcher retains the
same accessors that previously accepted arbitrary offsets. The change merely
gives destination bulk operations a 16-byte-aligned effective address whenever
the line is long enough. It does not claim to replace the backend instructions,
avoid an otherwise-invalid hardware access, or provide a measured speedup. No
benchmark result is asserted.

The optimized line function remains selected only by the existing ARM64 and
x86-64 feature conditionals. Other architectures retain the generic scalar
line implementation.

## Test-before evidence

The focused host test was first run against the pre-change line dispatcher. It
exited nonzero with `16-pixel path selected at unaligned destination offset 0`:
the prior implementation selected the 16-pixel operation immediately instead
of peeling destination offsets 0 and 1 to the aligned offset 2.

## Acceptance evidence

`Lambda64/tests/host/test-gui-bitblt-blend-alignment.sh` uses instrumented
scalar, quad, and interleaved adapters with identical pixel semantics. It must:

- compare the complete result, including untouched elements, with a scalar
  reference across every starting residue and lengths around scalar, quad, and
  16-pixel boundaries;
- reject any quad or interleaved call whose destination offset is not
  congruent to 2 modulo 4;
- observe the exact scalar prefix and subsequent batch calls for aligned,
  unaligned, short, zero-length, and differently aligned source cases; and
- pass alongside the overlapping BITBLT regression and Lisp source checks.

The work-item ledger also requires guest evidence. The host adapter proves the
dispatch and result contract but does not execute the real ARM64 or x86-64 SIMD
instructions in a Mezzano guest. This work item must not be marked verified
until an image-level guest run proves the aligned dispatcher with the native
backend.
