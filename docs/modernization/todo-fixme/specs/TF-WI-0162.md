# TF-WI-0162: IPv4 fragment reassembly contract

## Scope

This specification replaces the unconditional fragmented-packet discard in
`Lambda64/net/ip.lisp` with bounded inbound IPv4 reassembly. It covers packets
already accepted for a local unicast, interface broadcast, local broadcast, or
multicast destination. Unfragmented delivery remains unchanged. Outbound MTU
fragmentation is not expressed by the baseline receive-path directive and is
outside this work item.

## Required behavior

The 13-bit IPv4 fragment offset is interpreted in eight-octet units.
Reassembly state is keyed by source address, destination address, protocol, and
identification. Fragments may arrive in any order, but no payload is delivered
to `ipv4-receive` until sorted fragments provide one continuous byte range from
zero through the end declared by a fragment with `MF` clear. The completed
payload is delivered once as a private octet vector with start zero and end
equal to its length; receive buffers may therefore be reused immediately after
acceptance.

Non-final fragments must contain a positive multiple of eight data octets. An
empty fragment, a reconstructed payload beyond 65,515 octets or beyond the
65,535-octet total-length limit after accounting for the first header,
conflicting end
positions, a fragment extending beyond a known end, or a packet combining
fragmentation with `DF` is invalid. Any byte overlap, including a duplicate,
invalidates the entire matching datagram instead of permitting ambiguous
overwrite order.

At most 64 datagrams and 128 fragments per datagram may be retained. A resource
limit rejects new input rather than evicting live unrelated state. Incomplete
state expires after 60 seconds without an accepted fragment. The subsystem has
at most one delayed expiration callback pending, regardless of how many
datagrams complete or are rejected before it fires. Its handler removes stale
state and, when live state remains, schedules the next callback for the earliest
current deadline. Refreshing a datagram therefore cannot cause premature
expiration or accumulate abandoned per-datagram callbacks.

## Test-before evidence

Before implementation,
`bash Lambda64/tests/host/test-net-ip-state-and-fragments.sh` exited with status
1 because the required state and timeout forms were absent. The original
Ethernet receive method printed `not supported`, incremented the discard count,
and returned for every nonzero offset or `MF` bit.

## Acceptance evidence

`Lambda64/tests/host/test-net-ip-state-and-fragments.sh` executes the actual
fragment state machine with a deterministic clock and dispatch facade. It
verifies final/first/middle out-of-order completion, payload ownership after the
source buffer changes, overlap rejection and state removal, invalid non-final
alignment, offset/length overflow, exact timeout behavior, and independent
cleanup scheduling. It additionally invokes the real IPv4 Ethernet receive
method with final-first fragments and proves that only the single reconstructed
payload reaches the layer-four generic. A 200-datagram complete/reject stress
fixture proves that only one delayed callback exists, then invokes it with an
empty table and verifies that it does not reschedule itself.

The focused host test, Lisp style validation, documentation validation, and
whitespace-clean diffs cover deterministic local behavior. The ledger also
requires guest and integration evidence. No independent guest sender has yet
exercised real Ethernet fragments, checksum validation, NIC buffer reuse, and
UDP/TCP delivery, so this work item remains active. ICMP time-exceeded emission
for an expired first fragment is also not claimed by the current host evidence.
