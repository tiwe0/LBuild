# TF-WI-0318 — `WRAPPING-FIXNUM-+` 的溢出契约

- **基线标记：** `TF-occ-23752ae11b3ce2443b11da5d`
- **代码事实源：** `Lambda64/system/cas.lisp:80-92`、`Lambda64/compiler/backend/arm64/number.lisp`、`Lambda64/compiler/backend/x86-64/number.lisp`
- **风险：** high
- **要求测试层：** host、cold-image、integration

## 目标

`wrapping-fixnum-+` 必须拥有明确的 fixnum 宽度二补码包装语义，不能调用其溢出行为
未定义的 `%fast-fixnum-+`。为此，编译器后端提供专用的
`mezzano.compiler::%wrapping-fixnum-+` builtin；它在 tagged fixnum 表示上执行原始加法，
且不生成溢出到 bignum 的分支。

## 先测试证据

新增 `Lambda64/tests/host/test-system-wrapping-fixnum-add.sh`。它从生产源提取
`wrapping-fixnum-+` 和两个后端的 builtin，使用 63 位 fixnum 模型验证正、负溢出和
普通加法，并确认后端使用无溢出分支的原始加法。

实现前运行：

```sh
bash Lambda64/tests/host/test-system-wrapping-fixnum-add.sh
```

失败，因为生产源不存在专用 wrapping builtin，且 `wrapping-fixnum-+` 仍调用
`%fast-fixnum-+`。变异负例恢复该调用；测试必须拒绝变异。

## 验收标准

1. `most-positive-fixnum + 1` 包装为 `most-negative-fixnum`。
2. `most-negative-fixnum - 1` 包装为 `most-positive-fixnum`。
3. 非溢出 fixnum 加法与既有行为一致，非 fixnum 参数仍触发类型错误。
4. ARM64 与 x86-64 builtin 都使用原始加法，且不走 bignum 溢出路径。
5. cold image 与 QEMU integration 留待完整环境验收；在此之前工作项保持 `active`。

## 当前证据

```sh
bash Lambda64/tests/host/test-system-wrapping-fixnum-add.sh
```
