# TF-WI-0069: Atomic lexical-place support boundary

## Scope

This specification resolves the ambiguous lexical-variable entry in
`Lambda64/doc/atomic-extensions.md` without claiming an unimplemented compiler
feature.

## Required documentation contract

Lexical variables, including captured lexical variables, are not atomic places.
`get-cas-expansion` in `Lambda64/system/cas.lisp` consults the compiler
environment and signals `CAS on lexical variable ... not implemented.` when a
symbol resolves to a lexical variable instead of a special variable.

The documentation must distinguish this limitation from supported special
variables and aggregate places. It must also state that symbol macros are
expanded before the place is classified. Removing the old marker must not be
interpreted as adding lexical CAS support; implementing that capability still
requires the compiler extension identified in the source as a `casq`-style
operation.

## Test-before evidence

Before the documentation change, a focused `rg` scan found `Lexical variables
(TODO)` but no limitation or compiler behavior in the atomic extension guide.
The implementation already rejected the operation, so this work item changes
the documented contract rather than runtime behavior.

## Acceptance evidence

The following source-anchored static check must find the compiler rejection and
the environment lookup on which it depends:

```sh
rg -n 'lookup-variable-in-environment|CAS on lexical variable .* not implemented' Lambda64/system/cas.lisp
```

`make docs-check` and `git diff --check` validate repository paths, Markdown
structure, and whitespace. There is no runtime test because this slice does not
implement lexical CAS; the limitation remains explicit and testable at the
macro-expansion boundary.
