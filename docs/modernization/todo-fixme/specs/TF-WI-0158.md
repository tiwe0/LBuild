# TF-WI-0158: XTerm primary device attributes response contract

## Scope

This specification closes the missing primary Device Attributes response at
`Lambda64/gui/xterm.lisp:868` and defines its Telnet transport integration.

## Required behavior

The XTerm CSI parser must accept primary Device Attributes requests only in
their parameterless form (`CSI c`) or with the single parameter zero
(`CSI 0 c`). Each accepted request invokes a required terminal response
callback with the characters of `ESC [ ? 1 ; 2 c`, identifying a VT100 with
the Advanced Video Option. The callback is part of terminal construction and
must not have a no-op default.

Any other parameter list, including a nonzero parameter or more than one
parameter, remains unsupported and must follow the existing unknown-escape
path without emitting a response. A trailing separator is significant for
validation: `CSI 0 ; c` is not the single-parameter-zero form and must be
rejected even if the existing parameter representation normalizes it to the
same list as `CSI 0 c`.

The Telnet client must bind the callback to its client/connection lifecycle.
Every response character is encoded by `%telnet-encode-output` and written to
the current connection. The construction cycle is mediated by a lexical cell
and explicit setter. Invoking the callback before the client is bound or while
the client has no open connection must signal an error rather than silently
discard protocol output.

## Test-before evidence

Before implementation, the focused test was run against the original `HEAD`
sources with `XTERM_SOURCE` and `TELNET_SOURCE` overrides. It exited nonzero
because the original sources contained neither the Telnet response bridge nor
the XTerm response behavior. Re-running with the original XTerm source and the
then-current Telnet source also exited nonzero at the missing bridge boundary.

## Acceptance evidence

`Lambda64/tests/host/test-xterm-device-attributes.sh` must exercise the real
CSI character parser, verify the exact callback characters for both accepted
forms, verify rejection through the unknown path for `CSI 1 c` and
`CSI 0;0 c` and `CSI 0; c`, and send an accepted response through the Telnet bridge into a
capturing connection as octets `27 91 63 49 59 50 99`. It must also prove that
missing, NIL, and non-function callbacks are rejected by actual
`initialize-instance` execution, a function callback is accepted, and unbound
and disconnected bridge invocations signal.

The work-item ledger requires both host and guest evidence. The focused host
test, documentation validation, and diff whitespace validation cover only the
host-side contract and repository integrity. No guest execution evidence is
recorded yet, so this work item must not be marked verified until an image-level
guest test exercises the response through the real XTerm/Telnet runtime.
