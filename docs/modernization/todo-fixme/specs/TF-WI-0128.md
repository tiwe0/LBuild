# TF-WI-0128: ext4 non-leaf extent tree traversal contract

## Scope

This specification closes the nonzero extent-header depth requirement formerly
located in `do-file` in `Lambda64/file/ext4.lisp`.

## Required behavior

- A leaf node decodes and visits each 12-byte extent record in logical order.
- A non-leaf node decodes the 32-bit logical key and 48-bit child block address
  from each extent-index record, reads every child in key order, and recursively
  visits it until depth zero.
- Every child must advertise exactly one less level than its parent. Headers
  with a bad magic, a truncated body, or entry counts beyond either `eh_max` or
  the containing buffer's capacity are rejected rather than reinterpreted.
  `eh_max` must be positive, the root depth may not exceed five, and every
  non-leaf node must contain at least one entry.
- Index keys must increase strictly. Each child node's first key must equal its
  parent index key, and every descendant extent must remain inside the
  half-open range from that key to the next sibling key.
- Every extent-index child block must be below the superblock's `blocks-count`
  and is rejected before any disk read when it is outside that range.
- All leaf entries are decoded and validated before any file-data callback is
  invoked. Their logical ranges must be ordered and non-overlapping regardless
  of inode size or an early-returning callback.
- Existing depth-zero files remain on the same leaf decoding path.

## Test-before evidence

Before implementation, `do-file` explicitly rejected every root whose depth was
not zero. The initial focused test exited 1 because the required extent-index
structure and traversal did not exist. Follow-up adversarial runs exited 1 for
zero `eh_max`, a child whose first key differed from its parent, and an
out-of-range child block that was read before validation.

## Acceptance evidence

`Lambda64/tests/host/test-file-ext4-extents.sh` builds a two-level mock tree
above a leaf, runs the extracted production traversal, and verifies child and
data block reads in order. It also proves that a child advertising the wrong
depth signals an error. Corruption cases cover excessive root depth, zero node
capacity, empty non-leaf nodes, unordered indexes, parent/child key mismatch,
sibling-range crossing, leaf overlap and descending order, and child block
addresses at `blocks-count`.

Ext4 extent-block and superblock metadata checksum verification is not added by
these three baseline work items. This implementation validates structural and
range invariants but does not authenticate metadata protected by the ext4
metadata-checksum feature; checksum support requires its own filesystem-wide
compatibility and integration contract.

The focused host test passes. Guest and integration evidence against a real
ext4 filesystem with a non-leaf extent tree remains required before this item
can be marked verified.
