# TF-WI-0135: HTTP pathname junk parsing contract

## Scope

This specification resolves the `:junk-allowed` gap in
`Lambda64/file/http.lisp`. It covers HTTP host, optional port, and path parsing
through the file-system `PARSE-NAMESTRING` protocol.

## Required behavior

- A valid HTTP namestring returns both the pathname and the source position
  immediately after the parsed representation. A path introduced by `/` is
  part of the representation and is consumed in full.
- The optional leading `//` remains supported. The domain is non-empty and
  accepts ASCII letters case-insensitively, digits, hyphen, underscore, and
  dot. The default port is 80.
- An explicit port consists of a colon followed by one or more decimal digits.
- With `:junk-allowed t`, invalid trailing syntax after a valid domain or port
  terminates parsing and the second value identifies the first unconsumed
  character. A colon that is not followed by a decimal port remains entirely
  unconsumed, so the parsed prefix retains port 80.
- Without `:junk-allowed`, the same trailing syntax signals an error. Missing
  required domain syntax signals even when junk is allowed, because there is no
  valid pathname prefix to return.

## Test-before evidence

Before implementation,
`Lambda64/tests/host/test-file-http-remote-paths.sh` failed on the first valid
HTTP parse using `:junk-allowed t` with the old implementation's
`TODO: Junk-allowed` error.

## Acceptance evidence

The focused host test loads the parser form from the real source and verifies a
complete domain/port/path parse, a trailing-junk stop position, rollback of an
incomplete port, preservation of a complete explicit port before trailing junk,
rejection of both trailing-junk forms without junk permission, and rejection of
a missing domain.

The focused host test, `make lisp-style-check`, and a whitespace-clean diff are
required for this slice. The ledger also requires guest and integration
pathname coverage. Those levels are not recorded here, so this item remains
active.
