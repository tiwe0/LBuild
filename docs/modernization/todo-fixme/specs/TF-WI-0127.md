# TF-WI-0127: ext4 unwritten extent read contract

## Scope

This specification closes the unwritten-extent requirement formerly located in
`read-extent` in `Lambda64/file/ext4.lisp`.

## Required behavior

- `ee_block` is decoded as the full unsigned 32-bit logical block number and
  `ee_start_hi:ee_start_lo` remains a 48-bit physical block number.
- Values of `ee_len` through `#x8000` describe initialized extents. Larger
  values describe unwritten extents whose logical length is `ee_len - #x8000`.
  A zero logical length is rejected as corrupt metadata.
- Initialized extents read their physical blocks. Unwritten extents produce one
  filesystem-sized, zero-filled block per logical block and never read their
  recorded physical range.
- Every extent's physical range, initialized or unwritten, must end at or before
  the superblock's `blocks-count`. Unwritten extents return zeros but still
  describe allocated blocks. Validation covers the full extent even when the
  inode size would cause the read path to emit no blocks. An end exactly equal
  to `blocks-count` is valid.
- The logical half-open range `ee_block .. ee_block + length` must fit the
  32-bit ext4 logical-block address space. An end exactly equal to `2^32` is
  valid; an extent that ends beyond it is rejected.
- Sparse gaps before, between, or after extents likewise produce zero blocks so
  callback order continues to match the file's logical block numbers. Traversal
  stops at the block count implied by the inode size.
- The high halves of `blocks-count`, reserved-blocks-count, and
  free-blocks-count are shifted by 32 bits before they are combined with their
  32-bit low halves. Extent range validation therefore uses the actual 64-bit
  filesystem size.

## Test-before evidence

Before implementation, `read-extent` rejected every `ee_len` greater than
32768, truncated `ee_block` to 16 bits, and had no unwritten-block read path.
The first focused test run exited 1 while reporting the missing extent-index
structure needed by the complete shared traversal contract. A later
adversarial run exited 1 because an out-of-range extent-index block was read
before validation; after that boundary was fixed, the block-counter check
exited 1 because the high word was shifted by 64 rather than 32 bits. Strict
follow-up tests then exited 1 because an out-of-range unwritten extent was
accepted and because logical-end overflow had no dedicated validation.

## Acceptance evidence

`Lambda64/tests/host/test-file-ext4-extents.sh` executes the extracted
production readers and traversal. It checks both sides of the length marker,
zero-length rejection, a logical block number above 16 bits, 48-bit physical
address decoding, sparse leading data, and an unwritten extent whose placeholder
physical address is never read. It also exercises initialized ranges crossing
and ending exactly at `blocks-count`, rejection of an out-of-range unwritten
extent, logical ends at and beyond `2^32`, and the three high-word shift
expressions.

The focused host test passes. A guest mount/read of an ext4 image containing an
unwritten extent and the required integration run remain outstanding, so this
work item stays active.
