# TF-WI-0275: Obsolete snapshot metadata reclamation contract

## Scope

This item reclaims block-map and freelist metadata made obsolete by a committed
header update.

## Required behavior

- Read and retain the previous header roots before installing new roots.
- Make the new header durable before freeing any old metadata.
- Propagate every snapshot metadata or header write failure as a snapshot abort;
  a failed header publication must leave both old roots allocated.
- Release the temporary header page on both success and non-local failure.
- Traverse four block-map metadata levels, freeing structural blocks only and
  never leaf data blocks.
- Traverse the old freelist chain through word 511 and free every chain block.
- Skip reclamation when an old root equals its replacement. Freed metadata is
  represented in memory immediately and persisted by the next freelist image.

## Test-before evidence

The focused test reported the old block-map/freelist leak marker; no old header
roots were captured or traversed.

## Acceptance evidence

The executable host model validates a four-level synthetic block-map tree and a
two-block freelist chain, including exact metadata-only release order. It also
extracts and executes production `SNAPSHOT-WRITE-DISK` and `TAKE-SNAPSHOT`,
injects a failed header write, and verifies abort, header-page cleanup, and zero
old-root reclamation. Its success case proves durable header completion precedes
both reclamation callbacks, rejecting deletion of the header write. Power-loss
atomicity and long-running store-space recovery remain guest/storage validation.
