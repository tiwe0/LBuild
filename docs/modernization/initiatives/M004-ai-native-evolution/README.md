# M004 AI 原生演进基线

把模型放进系统的演进回路,让 Lambda64 能在不停机的前提下提出、验证并保留对自身的修改。

本文定义分期与门禁。具体设计放在各阶段自己的 ADR 或子 initiative 中。

## 问题

瓶颈不是"能不能在运行时改代码"。Lisp 系统本来就能——编译器是运行映像的一部分,任何函数、类、方法都能就地重定义,这一点从项目第一天就成立。

瓶颈是另外三件事,而它们都还不成立:

1. **系统无法被程序完整检视。** 要回答"当前有哪些应用、每个接受什么事件、暴露什么能力",目前只能 grep 源码。运行中的系统答不出来。
2. **改错了没有廉价的回滚与验证回路。** 快照恢复刚刚可用,但一次约 645 MB;guest 内没有"跑一下看对不对"的能力,测试全在宿主侧。
3. **没有因果记录。** 谁改了什么、基于什么判断、结果如何,没有地方记录。缺了这个,"演进"与"随机变异"没有区别。

### 为什么把可检视性排在第一位

2026-09-15 修复快照恢复的过程是直接证据。三处缺陷各自只有几十行改动,难点全部在"看不见":

- `entry.lisp` 中判断引导模式的 `debug-print-line` 探针**从未产出过任何输出**(它依赖的输出路径在引导早期尚未就绪),而缺陷恰恰是引导走错了分支。沉默被当成了信息。
- 一次恢复后 SWANK 报告 Desktop 与 Compositor 线程俱在,据此判定成功——而屏幕上是 `Display output is not active.`。**线程存活不等于设备可用。**
- 判定"卡住"还是"慢"反复出错,因为 `ps` 的 `%cpu` 是衰减平均值;换成累计 CPU 时间差才得到可用数据。

一个模型会遇到**相同且更严重**的困境:它不能 attach 到 tmux 看一眼屏幕,不能截图,不能凭直觉察觉"这个数字不对劲"。所以可检视性不是 AI 的铺垫,它本身就是当前的瓶颈;系统对人不可见,对模型只会更不可见。

## 非目标

- **不是加一个聊天应用。** 那是把模型当应用,与本 initiative 无关。
- **不是让模型直接改 supervisor。** 受限上下文的分配规则、引导路径的时序约束,连人都会反复踩错(见 D020、本文上节)。模型进入的应该是有检查点保护、有验证回路的区域。
- **不追求全自动。** 目标是让"提出—验证—保留或回滚"这条链路可用且可审计,人在其中的位置由后续阶段决定。

## 现状盘点

已经具备的:

| 能力 | 状态 | 证据 |
| --- | --- | --- |
| 编译器在运行映像内 | 可用 | 经 SWANK 就地重定义、重新编译 |
| 活系统检视 | 部分 | 能查线程、全局量、设备认领状态;无法枚举"应用"与"能力" |
| 状态持久化 | 可用 | 快照恢复 56 秒回到完整桌面 |
| 快速迭代层 | 可用 | GUI 与 applications 全部 46 个文件在第四阶段,改动无需冷重建,见[重建矩阵](../../../development/rebuild-matrix.md) |
| 错误不致命 | 可用 | IPL 之后出错挂起线程而非停机,SWANK 仍可连入 |

尚不具备的,按阻塞程度:

| 缺口 | 影响 |
| --- | --- |
| 应用是隐式概念 | 九个应用在九个包中各自定义同形的 `dispatch-event`,合计 61 个方法,事件集几乎完全一致。"有哪些应用"无法被查询 |
| guest 内无验证回路 | 改动只能靠宿主测试或人眼确认 |
| 检查点昂贵 | 一次快照约 645 MB / 30 秒,见 D025 |
| 无变更记录 | 无法区分演进与随机变异 |

## Stage A:让系统能描述自己

**入口**:无前置,可立即开始。

**工作**:

- 把隐式的应用协议提升为显式协议:统一的泛函与基类,取代九份复制。**先原样提升,不改语义**——九个现有实现是验收锚点,行为不变即正确。
- 让应用成为**可枚举的数据**:有哪些、各自接受什么事件、暴露什么入口。
- 同等对待 UI:窗口、控件、字体度量应当可列举、可检视,而不只是可绘制。
- 补齐引导与运行期的**有效探针**。原则是:探针的沉默必须有意义——要么确知它会产出,要么不要依赖它。

**退出**:能从 REPL 问出"这个系统现在有什么",答案由运行中的系统给出,而非源码扫描。

**与 Phase 4 的关系**:[路线图 Phase 4](../../roadmap.md) 已列出"结构化 app descriptor、app/window session、稳定 compositor API"。Stage A 与之是同一批工作,本文只是给出它在 AI 方向上的判据。

## Stage B:让改动可回滚、可验证

**入口**:Stage A 的应用与 UI 可枚举。

**工作**:

- 降低检查点成本至可随时使用。D025 的两项——每页一次同步磁盘往返、ARM64 上脏页追踪关闭——前者已有改善,后者需独立设计。
- 建立 **guest 内的验证回路**:系统内能运行一组断言并给出结构化结果,不依赖宿主。
- 变更的**因果记录**:改了什么、依据什么、验证结果如何、是否保留。

**退出**:一次改动可以在系统内完成"应用—验证—保留或回滚",全过程留下可审计记录。

## Stage C:把模型放进回路

**入口**:Stage B 的回路对人可用——**人用着不顺手的回路,模型用只会更差**。

**工作**:

- 模型作为系统的可调度组件,而非应用:能查询状态(Stage A)、提出改动、在检查点保护下应用、用验证回路确认、失败回滚(Stage B)。
- 明确权限边界:模型可改的区域、需要人确认的区域、禁止区域。参考现有的[禁止分配上下文](../../../development/allocation-forbidden-contexts.md)——那是一类已经写清楚的硬约束。

**退出**:模型提出的改动能走完完整回路并留下记录。

## 贯穿性原则

- **每一步都以"人能不能用"为先验收。** 三个阶段的能力对人和对模型是同一套;人用不了的,模型一定用不了。
- **先提升,后改造。** 抽象既有协议时不要顺手改语义,否则失去"行为不变即正确"这个锚点。
- **探针的沉默必须有意义。** 这是本项目付过代价的教训。
- **优先在第四阶段的 46 个文件里工作。** 迭代以分钟计;supervisor 与 runtime 的改动要冷重建加完整冷引导。

## 风险

- **Stage A 的抽象可能被 UI 改造牵引变形。** 若两者并行,接口形状会迁就当时的渲染需要,而那正是要改变的部分。故 Stage A 的协议提升应先于 UI 改造完成。
- **`settings` 与 `spy` 是检验样本。** 另外七个应用实现完全一致,对抽象没有信息量;这两个处理的事件集更少,会暴露"未实现的事件默认如何处理"这个真问题。
- **`mezzano.gui.widgets` 已是半个框架。** 抽象应用时须先划清它与新协议的边界,否则会出现两层做同一件事。
